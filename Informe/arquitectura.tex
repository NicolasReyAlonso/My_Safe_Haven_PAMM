\section{Arquitectura}
Las arquitecturas que hemos decidido utilizar para el desarrollo de esta aplicación son las siguientes:
\begin{center}
    \textbf{\textit{Clean Architecture + MVVM + Jetpack (Compose/Views)}}
\end{center}

\subsection{MVVM}
El patrón \textit{Model–View–ViewModel} (MVVM) nos permite separar de forma efectiva la lógica de presentación de la lógica de la interfaz.
 Esto facilita el mantenimiento del código y reduce el acoplamiento entre componentes. 
 Las principales ventajas por las que elegimos este patrón son:

\begin{itemize}
    \item Permite que las vistas contengan únicamente lógica de interfaz, manteniendo un código más limpio y fácil de extender.
    \item Los \textit{ViewModels} soportan persistencia de estado incluso frente a cambios de configuración,
    como la rotación de pantalla.
    \item Incrementa la capacidad de realizar pruebas unitarias al separar las responsabilidades dentro del flujo de datos.
\end{itemize}

\subsection{Clean Architecture}
La \textit{Clean Architecture} garantiza una separación clara entre las reglas de negocio, 
los datos y la interfaz de usuario. Esta división en capas mejora considerablemente la escalabilidad y 
mantenibilidad del sistema. Lo seleccionamos debido a sus siguientes beneficios:

\begin{itemize}
    \item Define límites bien estructurados mediante capas independientes: dominio, datos y presentación.
    \item Permite encapsular la lógica central de negocio en casos de uso (\textit{use cases}), 
    facilitando la evolución del proyecto sin afectar otras capas.
    \item Facilita la integración de servicios externos, como APIs, sensores de ubicación o bases de datos locales.
    \item Reduce el acoplamiento, lo que permite sustituir componentes (por ejemplo, cambiar la base de datos local) 
    sin modificar la lógica interna.
    \item Mejora considerablemente la capacidad de realizar pruebas, especialmente sobre reglas de negocio.
\end{itemize}

\subsection{Jetpack (Compose/Views)}
El ecosistema \textit{Jetpack} nos proporciona herramientas modernas y altamente optimizadas para el desarrollo de 
interfaces y funcionalidades móviles. Dentro del proyecto empleamos tanto \textit{Compose} como vistas 
tradicionales (\textit{Views}), según las necesidades de cada pantalla. Las razones principales para utilizar estas 
tecnologías son:

\begin{itemize}
    \item \textit{Jetpack Compose} permite crear interfaces declarativas, más intuitivas y fáciles de mantener.
    \item Ofrece integración natural con \textit{ViewModels}, \textit{StateFlow} y otros componentes de arquitectura.
    \item Simplifica el manejo del estado y el renderizado dinámico de la UI.
    \item Framework optimizado por Google para el desarrollo moderno de Android, asegurando compatibilidad y evolución a largo plazo.
\end{itemize}

\subsection{Estructura del proyecto}
La estructura del proyecto sigue las capas definidas por la \textit{Clean Architecture}, organizando el código en
módulos claramente diferenciados:
\begin{itemize}
    \item \textbf{Capa de Dominio:} Contiene las entidades y casos de uso que encapsulan la lógica de negocio.
    \item \textbf{Capa de Datos:} Gestiona la persistencia y recuperación de datos, incluyendo repositorios e integraciones con APIs externas.
    \item \textbf{Capa de Presentación:} Incluye las vistas, \textit{ViewModels} y componentes UI, utilizando \textit{Jetpack Compose} y vistas tradicionales.
\end{itemize}
Esta organización modular facilita la colaboración entre desarrolladores, mejora la mantenibilidad del código y 
permite una evolución más sencilla y controlada del proyecto a lo largo del tiempo. \newline
Asimismo, la alta presión de tiempo nos ha llevado a tomar decisiones rápidas en cuanto a la arquitectura y 
tecnologías a utilizar, acabando con una estructura de proyecto un poco "espagueti" en ciertos puntos, pero funcional y
adaptada a nuestras necesidades inmediatas. De forma concreta el proyecto se estructura en las siguientes 
carpetas principales:
\begin{itemize}
    \item \textbf{Backend:} Contiene el código del backend desarrollado en python Flask, 
    incluyendo rutas, controladores y modelos de datos, así como el Dockerfile para su despliegue.
    \item \textbf{Frontend:} Incluye todo el código de la aplicación móvil.
    \item \textbf{Informe:} Contiene el código fuente del informe en LaTeX.
    \item \textbf{Documentación:} Incluye documentación adicional, diagramas y recursos relacionados con el proyecto.
    \item \textbf{Presentación:} Contiene los archivos de la presentación del proyecto en LaTeX.
\end{itemize}
Como la parte más relevante del proyecto es la aplicación móvil, a continuación se detalla la estructura interna de la 
carpeta \textbf{Frontend}:

Breve descripción y correspondencia con MVVM / Clean Architecture:
\begin{itemize}
  \item \textbf{data/}: Implementación de fuentes de datos — almacenamiento local (preferences, DataStore), gestión de ubicación y clientes remotos (Retrofit). Aquí también están los \textit{repositories} que abstraen el acceso a datos y aplican transformaciones necesarias.
  \item \textbf{domain/model/}: Entidades del dominio (modelos puros) que representan los conceptos de la aplicación (Haven, Post, User, etc.). En una práctica completa, los casos de uso (use-cases) vivirían aquí.
  \item \textbf{presentation/}: Contiene la UI y los \textit{ViewModels}. Las \textit{screens} y componentes son la 
  "View" (Compose/Views), y los archivos en \texttt{viewmodel/} implementan la lógica de presentación y 
  exponen estados/acciones.
  \item \textbf{di/}: Configuración de inyección de dependencias (p. ej. Hilt o Koin) para proveer repositorios, 
  clientes API y ViewModels. Asimismo, tambien incluimos algunos modelo tras una refactorización por falta de tiempo.
  somos conscientes de que no es la estructura ideal, pero es funcional y cumple con los requisitos del proyecto.
  \item \textbf{MainActivity.kt} y \textbf{MyApplication.kt}: puntos de entrada de la app; inicializan navegación, 
  tema global e inyección de dependencias.
\end{itemize}

Esta organización facilita separar responsabilidades.
